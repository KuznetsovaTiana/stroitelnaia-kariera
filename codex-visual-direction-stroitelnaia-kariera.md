# Дополнительное визуальное направление для Codex

## Назначение документа

Этот файл является дополнением к `codex-task-stroitelnaia-kariera-v2.md`.

Он **не заменяет и не отменяет** требования основного ТЗ. Если между этим документом и `codex-task-stroitelnaia-kariera-v2.md` возникает противоречие, приоритет имеет основное ТЗ.

Задача этого файла — объяснить желаемое **ощущение интерфейса, визуальную иерархию и композиционные принципы** на основе приложенного визуального референса мобильной навигации.

Референс воспринимать как **концептуальный пример**, а не как макет для буквального копирования. Не нужно воспроизводить iPhone, конкретные цвета, размеры карточек или расположение элементов пиксель в пиксель. Нужно перенести сам принцип: спокойный, чистый, понятный role-based интерфейс, в котором сначала видны задачи пользователя, а навигация и служебные функции не конкурируют с контентом.

---

# 1. Главный принцип

Пользователь должен видеть не «все возможности платформы», а только то, что относится к:

- его текущей роли;
- его текущему состоянию;
- его ближайшим задачам;
- доступным ему действиям.

На первом мобильном экране после компактной шапки практически сразу должен начинаться **полезный рабочий контент**.

Недопустимо, чтобы пользователь сначала прокручивал:

- несколько рядов меню;
- публичные ссылки;
- переключатель роли;
- настройки демонстрации;
- каталог модулей;
- служебные пояснения;

и только после этого доходил до основной задачи.

---

# 2. Одна навигация вместо нескольких

Для мобильной версии использовать **одну основную навигационную систему**.

Для ролей, где это уместно, предпочтителен `bottom navigation` из 4–5 ключевых разделов.

Пример для работодателя:

- Главная
- Отклики
- Объявления
- Практиканты
- Ещё

Не создавать одновременно:

- верхнее меню;
- второй набор текстовых ссылок;
- каталог модулей;
- отдельное меню тех же разделов;
- дополнительные публичные ссылки в рабочем кабинете.

Навигация должна быть понятной без изучения структуры проекта.

---

# 3. Экран «Ещё»

Экран `Ещё` должен выполнять роль аккуратного второго уровня навигации.

Функции группируются **по смыслу**, а не просто перечисляются подряд.

Пример:

## Компания

- Команда
- Сообщения
- Поддержка
- Настройки компании, если они есть

## Демонстрация

- Сменить роль
- Учебная дата
- О демонстрации
- Сбросить демоданные

Отдельно внизу:

- На публичный сайт

Публичный сайт, рабочий кабинет и инструменты демонстрации — это **три разных навигационных контекста**.

Не смешивать их на одной поверхности.

---

# 4. Полностью убрать «Каталоги и модули демонстрации»

Полностью убрать из рабочих кабинетов универсальный блок вида:

`Каталоги и модули демонстрации`

Не заменять его другим общим списком всех страниц сайта.

Каждая существующая функция должна получить одно естественное место:

1. в основной навигации конкретной роли;
2. в контекстном переходе внутри текущей задачи;
3. во вторичных настройках соответствующего раздела;
4. на публичном сайте;
5. в инструментах демонстрации.

Не использовать интерфейс как sitemap проекта.

Пользователь не должен видеть все маршруты только потому, что они существуют в коде.

---

# 5. Dashboard каждой роли должен быть task-first

Главная каждой роли должна начинаться с того, **что требует внимания сейчас**.

Для работодателя первый смысловой блок может быть:

## Что требует внимания

- 3 новых отклика
- 1 документ на проверке
- 4 практиканта

Это пример структуры, а не требование использовать именно эти цифры.

Количество и карточки должны формироваться из реального текущего demo-state.

**Не добавлять фальшивые счётчики ради композиции.**

При нулевом количестве:

- не оставлять бессмысленные карточки вроде `0 новых откликов`, если они не помогают;
- использовать содержательное empty state;
- либо не выводить этот приоритетный блок.

---

# 6. Что должна содержать задача на dashboard

Карточка задачи должна содержать минимум информации, достаточный для понимания следующего шага:

- что произошло;
- к чему относится;
- требуется ли действие пользователя;
- основной CTA.

Пример:

`3 новых отклика`  
`На ваши объявления`  
`Посмотреть`

Лучше короткая понятная карточка, чем длинный блок со статусами, служебными полями и техническими пояснениями.

В каждой смысловой карточке должен быть **один очевидный основной CTA**.

Вторичные действия не должны иметь такой же визуальный вес.

По возможности вся безопасная карточка или строка списка может быть кликабельной, но семантика ссылок/кнопок и клавиатурная доступность должны оставаться корректными.

---

# 7. Не превращать dashboard в каталог карточек

Не создавать сетку из десяти одинаково важных блоков.

Приоритет:

1. актуальные задачи;
2. состояние текущих процессов;
3. быстрые действия;
4. вторичная информация;
5. аналитика;
6. справочные данные.

Блок `Быстрые действия` допустим только для действительно частых операций:

- Создать объявление;
- Посмотреть отклики;
- Найти кандидатов;
- открыть аналитику, если она действительно нужна роли.

Не использовать `Быстрые действия` как новый каталог модулей.

---

# 8. Демо-режим должен быть компактным

Активная роль должна быть всегда понятна, но demo-state не должен занимать четверть экрана.

На мобильном достаточно компактной строки/чипа вида:

`Демо · Работодатель · Алексей Громов ▾`

По нажатию открывается отдельная панель с demo-инструментами.

Не держать в основном потоке крупными отдельными элементами:

- Начать заново;
- Учебная дата;
- О демонстрации;
- выбор роли;
- выбор пользователя.

`Сбросить демоданные` считать служебным destructive action.

Он должен находиться внутри раздела демонстрации и требовать понятного подтверждения последствий.

---

# 9. Уведомления

Уведомления лучше оставить глобальным элементом в шапке с бейджем, а не отдельным крупным пунктом меню.

При этом различать:

- обычные уведомления;
- изменения статуса;
- задачи, которые требуют действия.

Пользователю важнее знать:

`2 требуют действия`

чем просто:

`13 уведомлений`.

---

# 10. Шапка мобильного интерфейса

Шапка должна быть компактной.

Допустимая структура:

- логотип / короткий бренд;
- название платформы или сокращённый вариант;
- уведомления;
- кнопка дополнительного меню.

Не занимать несколько экранных строк навигационными ссылками.

После шапки пользователь должен почти сразу видеть рабочий контент.

---

# 11. Визуальный стиль

Сохранить текущую стилистику проекта:

- тёплый молочный фон;
- графитовая типографика;
- тонкие границы;
- архитектурная сдержанность;
- спокойная современная композиция.

Не превращать интерфейс в яркий типовой SaaS-dashboard.

Допустимы мягкие смысловые оттенки:

- зелёный — завершено / успешно;
- нейтральный — информация;
- тёплый предупреждающий — требуется внимание;
- красный — ошибка / опасное действие.

Цвет не должен быть единственным носителем смысла.

Всегда должна быть текстовая подпись.

Не использовать большое количество разноцветных декоративных иконок только ради красоты.

---

# 12. Плотность интерфейса

Избегать чрезмерно крупных карточек.

На мобильном одна простая задача не должна занимать треть экрана без необходимости.

Интерфейс должен быть достаточно плотным, но не тесным.

Не использовать гигантские вертикальные отступы, которые заставляют постоянно прокручивать экран.

При этом не уменьшать touch-target ради компактности.

Основные интерактивные элементы должны оставаться удобными для пальца.

---

# 13. Иерархия текста

Текстовая иерархия должна быть очевидной:

1. назначение страницы;
2. актуальное состояние или задача;
3. основное действие;
4. детали;
5. служебная информация.

Служебные обозначения вроде:

- `КАРКАС / ЭТАП B–C`;
- кодов экранов;
- внутренних статусов;
- технических enum;

не должны визуально конкурировать с пользовательской информацией.

Они должны исчезнуть из обычного рабочего UI в соответствии с основным ТЗ.

---

# 14. Внутренние ссылки

Не использовать `↗` для обычных внутренних переходов.

Такой знак оставлять только там, где действительно открывается внешний ресурс или отдельный внешний контекст.

Внутренние ссылки должны выглядеть как обычные элементы навигации приложения.

Не разбрасывать десятки голых текстовых ссылок по странице.

Если действия связаны семантически — объединять их в раздел, меню или контекстную группу.

---

# 15. Desktop и mobile — одна архитектура

На desktop сохранить те же принципы, но не копировать мобильный bottom navigation буквально.

Desktop может использовать:

- аккуратную боковую навигацию;
- компактную верхнюю навигацию;
- комбинацию sidebar + contextual header.

Но структура разделов и приоритеты должны совпадать с mobile.

Mobile и desktop — две композиции одной информационной архитектуры, а не два разных продукта.

---

# 16. Ожидаемая структура роли работодателя

## Главная

- задачи;
- новые отклики;
- документы;
- состояние практикантов;
- ближайшие действия.

## Объявления

- вакансии;
- практики;
- стажировки;
- черновики;
- модерация;
- архив.

## Отклики

- входящие кандидатуры;
- требуют действия;
- в работе;
- ожидаем ответ;
- завершённые.

## Практиканты

- активные практики;
- документы;
- задания;
- отчёты;
- проблемные состояния.

## Компания

- профиль компании;
- команда;
- настройки;
- связанные функции.

`Кандидаты`, если остаётся отдельной функцией, должны находиться там, где это естественно для текущей архитектуры работодателя, а не становиться ещё одним случайным глобальным пунктом.

---

# 17. Ожидаемая структура роли студента

Для студента не копировать меню работодателя.

Ориентир:

- Главная
- Поиск
- Отклики
- Моя практика
- Профиль

Главная студента прежде всего должна отвечать:

`Что мне нужно сделать сейчас?`

Приоритеты:

- если пришло предложение — оно важнее рекомендаций вакансий;
- если возвращён документ — исправление документа важнее каталога;
- если идёт практика — текущее задание важнее поиска;
- если активных обязательств нет — можно показывать поиск и рекомендации.

---

# 18. Ожидаемая структура роли координатора вуза

Главный экран координатора должен быть похож на рабочую очередь.

Пример:

- Требуют согласования
- Возвращённые / исправленные документы
- Отчёты
- Итоговые решения
- Просроченные / проблемные практики

Не заставлять координатора сначала выбирать студента, чтобы узнать, есть ли по нему работа.

Полный список студентов должен оставаться отдельным реестром, а не главным рабочим экраном.

---

# 19. Ожидаемая структура роли оператора

Рабочий интерфейс оператора должен ощущаться как moderation/work queue.

Пример:

- Компании на проверке
- Объявления на модерации
- Обращения
- Проблемы данных
- Справочники

Не превращать кабинет оператора в публичный каталог платформы.

---

# 20. Не удалять функционал при упрощении навигации

Очень важно: удаление пункта из глобального меню **не означает удаление возможности**.

Функция должна получить более логичное место.

Перед удалением старой навигации составить mapping:

`старый маршрут → новая точка входа → роли, которым он доступен`

После переработки проверить, что ни одна разрешённая функция не стала недоступна.

---

# 21. 404 / forbidden / устаревшие ссылки

Для ошибок использовать новый чистый каркас.

Не показывать огромный каталог навигации над сообщением об ошибке.

Пример:

## Страница недоступна

Возможно, ссылка устарела или этот раздел недоступен текущей роли.

`Вернуться на главную работодателя`

Если есть полезный контекст — предложить релевантный маршрут, а не универсальный список всех страниц.

---

# 22. Не делать всё карточкой

Использовать разные паттерны по назначению:

- карточки — для задач и смысловых групп;
- обычные строки — для меню и компактных списков;
- таблицы — для плотных административных данных;
- секции — для структурирования процессов;
- stepper — для последовательных этапов;
- чек-лист — для подготовки документов / обязательных действий.

Не злоупотреблять:

- скруглениями;
- тенями;
- цветными кружками;
- декоративными плашками.

Они должны поддерживать визуальную систему проекта, а не превращать её в типовой banking/SaaS UI.

---

# 23. Главный визуальный критерий

На любом рабочем экране за 2–3 секунды должно быть понятно:

**Где я?**  
**Какая у меня роль?**  
**Что сейчас важно?**  
**Что я могу сделать?**

Если для ответа на эти вопросы пользователь должен сначала:

- изучить меню;
- прокрутить служебные блоки;
- раскрыть каталог модулей;
- догадаться по статусам;

интерфейс ещё не исправлен.

---

# 24. Обязательная визуальная проверка после реализации

Перед завершением задачи сделать реальные скриншоты минимум:

- работодатель: главная mobile 390 px;
- работодатель: экран `Ещё`;
- студент: главная mobile;
- координатор: главная mobile;
- оператор: главная mobile;
- соответствующие desktop-главные.

Посмотреть на них именно как на композицию, а не только проверить отсутствие overflow.

Если верхняя половина мобильного экрана снова занята:

- навигацией;
- demo-инструментами;
- служебной информацией;

переработка считается неудачной.

Если в рабочем кабинете снова появился универсальный список:

`Компании / Вузы / Профессии / Статистика / Помощь / ...`

проблема считается не исправленной.

Если все роли получили практически одинаковый dashboard с заменёнными подписями, проблема считается не исправленной.

---

# 25. Как использовать приложенный визуальный референс

Приложенная картинка показывает не обязательный финальный дизайн, а желаемое направление.

Из неё нужно взять:

- одну навигацию вместо нескольких;
- рабочие задачи наверху;
- компактную демонстрационную панель;
- отдельный второй уровень `Ещё`;
- смысловую группировку функций;
- отделение публичного сайта от кабинета;
- отсутствие универсального каталога модулей;
- спокойную визуальную иерархию;
- хорошую сканируемость мобильного экрана.

Не нужно буквально копировать:

- форму смартфона;
- цвета иконок;
- размеры карточек;
- конкретные тени;
- отдельные декоративные решения;
- числовые значения из примера.

Финальная цель — не копия референса.

Финальная цель — добиться такого же уровня ясности, визуальной иерархии и ощущения, что каждая роль получила собственное рабочее пространство.

---

# 26. Три обязательных принципа

1. **Не копировать картинку пиксель в пиксель. Копировать принцип иерархии.**
2. **Удаление «Каталога модулей» означает перераспределение функций по естественным местам, а не перенос того же списка в другое меню.**
3. **На первом мобильном экране рабочая задача должна появляться раньше служебной информации.**

---

# 27. Связь с основным ТЗ

Этот документ должен применяться совместно с:

`codex-task-stroitelnaia-kariera-v2.md`

Основной файл содержит:

- функциональные дефекты;
- архитектуру ролей;
- требования к статусам и next action;
- сценарии практики;
- мобильные проверки;
- доступность;
- QA;
- критерии приёмки.

Этот файл уточняет только желаемое **визуальное и композиционное направление**.

При конфликте всегда следовать основному ТЗ.
